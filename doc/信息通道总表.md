# 信息通道总表（现有代码用到哪些通道 · 各能拿到什么）

> 口径：**生产代码扫描**（43 个 `.lua`，排除 `tests/` 与 `node_modules/tmp` 等）+ **真机实测**（见 `doc/通道信息记录.md`）。
> 生成时间：2026-09-25。★代码改动后请重跑 §G 的扫描脚本刷新本表。

## 0. 通道分四类

| 类 | 通道 | 特点 |
|---|---|---|
| **A 事件通道** | `Frame:RegisterEvent(名字)` | 只有事件名**真的存在**才会来；名字官方**无索引**（85 个分类里没有 Events）⇒ 必须真机验证 |
| **B 取值 API** | `Unit*` / `Get*` / `Is*` / `Check*`（101 个） | 主动读，随时可读；**只能读已知 unit id**（无敌人枚举） |
| **C 窗口 / 消息组** | `GetChatWindowMessages` / `Add|RemoveChatWindowMessages` / `ChatFrame_OnEvent` / `RegisterAllEvents` / `IsEventRegistered` | 窗口级与「全事件」级入口 |
| **D tooltip 通道** | 自建隐形 `EVAL_HELP_WTT` + `GameTooltip:SetXXX` | 读客户端**没暴露成 API** 的信息（唯一入口） |

## D. 窗口 / 消息组 / 事件系统入口

| 入口 | 能做什么 | 实测结论 |
|---|---|---|
| `ChatFrame_OnEvent`（普通全局函数） | **不依赖事件名**截获一切进聊天窗的文本；三形态取参（`event`+全局 `arg1..9` / `(event,文,发送者)` / `(self,event,文,…)`） | ✅ 55 条经过、0 条取不到文本；★`frame.AddMessage` 包装**写不生效**（0/8） |
| `RegisterAllEvents` / `UnregisterAllEvents` | 全事件抓取（把「真实存在的事件名」读出来） | ✅ 一轮抓到 53 个事件名 |
| `IsEventRegistered(frame, 事件)` | 反查「客户端认不认这个名字」 | ✅ 可用但返 **1 不是 true**；★**不在官方索引里** |
| `GetChatWindowMessages(win)` | 读某窗口订阅的消息组名串 | ⚠️ 本客户端**战斗文字不挂消息组**（窗口2 只有 `COMBAT_ERROR`）⇒ 这条推导不成立 |
| `Add/RemoveChatWindowMessages` | 官方「某类消息不显示」开关（频道进出屏蔽） | ✅ 唯一实测有效的屏蔽路（Lua 打印层在本客户端是死的） |
| `ScrollingMessageFrame`（`ChatFrame1..7` 的基类） | 16 条方法全是**写/滚动/样式** | ❌ **无 `GetMessageText`/`GetNumMessages`** ⇒ 窗口内容读不回来 |

## E. 已确认拿不到（否定清单，别再试）

| 想要的信息 | 结论 |
|---|---|
| 结构化战斗日志 | 无 `COMBAT_LOG_EVENT_UNFILTERED` / `GetNumCombatLogMessages` / `CombatLogGetCurrentEventInfo`（那是 2.4+）；`LoggingCombat` 只写人类可读文件且**插件无文件 API**，本机 `Saved` 下连 Logs 目录都没有 |
| 引擎/Lua 日志 | `UELog` 调用成功但**什么都不落盘**；`RLog` 仅 debug 构建 ⇒ 本项目改用 SavedVariables 环缓冲 |
| 仇恨 / 威胁 | 官方索引 **0 条** |
| 敌人 / 附近单位枚举 | **0 条** ⇒ 只能 `TargetNearestEnemy` 循环切目标（已降级为手工命令） |
| 读条信息（`UnitCastingInfo`） | 没有 ⇒ 只能靠 `SPELLCAST_*` 事件 |
| 精确距离数值 | 无 SuperWoW ⇒ 只有 `IsActionInRange` / `CheckInteractDistance` 的粗档 |
| 事件名清单（官方） | **无 Events 页**（85 个分类里没有）⇒ 只能 `RegisterAllEvents` 实测 |

## F. 实测坑（与通道有关的）

1. **`PLAYER_TARGET_CHANGED` 频率不稳定**：一轮 624 次/59.8s（≈10/s）、另一轮 135 次/229.8s（≈0.6/s）⇒ 前者很可能是**别的插件在切目标**。主插件在这条事件上挂的是**全量** `EVAL_HELP_UPDATE_STATE()`，建议加 0.15~0.2s 去抖防峰值，并先查是谁在切目标。
2. `UNIT_HEALTH` 176 次 / 60s ⇒ 高频 meta 事件**不许**进样本池（曾把 8 条原始样本占满）。
3. 聊天事件的**正文一律在 `arg1`**、`arg2/arg3` 为 `nil`（例外：`CHAT_MSG_ADDON` = 插件名/荷载/频道）。
4. `IsEventRegistered` 返 **1 不是 true**；判据写 `(r == true or r == 1)`。
5. `CHAT_MSG_COMBAT_HOSTILE_DEATH` 对同一只怪发**两条**（`你杀死了X！` + `X死亡了。`）⇒ 计数必须去重。
6. `CHAT_MSG_COMBAT_CREATURE_VS_PARTY_HITS` = 怪打**队友** ⇒ **绝不能进「围攻我」的桶**。
