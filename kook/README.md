## 10 条关键结论（先看这个）

1. **频道维护需要的 HTTP 接口是齐的**：`channel/list|view|create|update|delete` + `channel-role/index|create|update|sync|delete`（权限覆写）+ 语音三部（`channel/user-list`、`channel/move-user`、`channel/kickout`）。没有任何一个「未知/缺失」的必需能力。
2. **`channel/list` 返回的是「精简频道」**：只有 `id / user_id / parent_id / name / type / level / limit_amount / is_category` 八个字段，**不含 `topic`、`slow_mode`、权限覆写** ⇒ 想做全量对账，要么逐个 `channel/view`（N+1 次请求，受限于限流），要么用 `guild/view`（**一次拿到 `channels[]` + `roles[]`**，是冷启动首选），要么靠事件增量。
3. **`channel/create` 能设置的字段极少**（`guild_id / name / parent_id / type / limit_amount / voice_quality / is_category`）⇒ **无法在创建时写 `topic`、`slow_mode`、权限**。建一个「完全符合规格」的频道 = `create` 1 次 + `update` 1 次 + 权限覆写 N 次。这直接决定了限流预算（见结论 8）。
4. **创建分组的传参是「独占」的**：`is_category=1` 时**只接受 `guild_id / name / is_category` 三个字段**（官方原文），多传字段的行为未文档化 ⇒ 待实测（T6）。
5. **排序只能逐条写**：没有批量重排接口，`level` 只能靠 `channel/update` 一条条改 ⇒ 一次重排 = N 次写请求 + **N 个自己触发的 `updated_channel` 事件**（事件风暴与限流都要按这个量级设计）。`level` 的**方向、相同值行为、分组与频道是否共用同一序空间**官方**没定义**（T2）。
6. **权限模型是「角色权限位 ⊕ 频道覆写」两层**：权限是一个 unsigned int 的 31 个比特位（bit5=`32` 频道管理，bit11=`2048` 查看频道，bit0=`1` 管理员可绕过全部频道权限）。频道级通过 `channel-role/*` 写 `allow`/`deny`；**在分组频道上写覆写会级联到所有 `permission_sync=1` 的子频道**（官方明确）。官方**没有**「最终生效权限计算」接口 ⇒ 要自己算。
7. **事件是有的，而且是「全量系统消息」**：频道三事件 `added_channel` / `updated_channel` / `deleted_channel`，角色三事件 `added_role` / `updated_role` / `deleted_role`，外加服务器/成员/消息/语音进出等。投递走 **WebSocket 或 Webhook，两者互斥**（官方明确：设了 Webhook 就不能再用 WS 收）。**订阅机制确实存在**：`user/me` 返回里有 `intent`（官方注为「事件订阅掩码，默认 -1 接收所有」），但各位含义与设置方式未文档化（T16）；「机器人无查看权限的频道是否推送」也未说明（T1）。
8. **限流是「分桶 + 响应头自适应」**：每个响应带 `X-Rate-Limit-Limit / -Remaining / -Reset / -Bucket / -Global`，超限返回 **HTTP 429**（头照旧），**多次超速会被禁用 bot**（官方原文：可能撤销 API 密钥并限制登录）。文档只给了示例值（`Limit: 5`、`Reset: 14`），**各接口的具体桶值未公开** ⇒ 只能运行时读头（T9）。
9. **消息有「账号级」每日配额**：同一开发者账号下所有机器人**单日 10,000 条**（北京时间 12:00 重置），`message/create` 与 `message/update` **都计数** ⇒ 频道的「维护通知 / 频道导航置顶」必须低频，且优先复用同一条消息。
10. **三个高危事实**（写代码前必须知道）：
   - `channel/delete` **没有回收站、没有恢复接口**，删了就是删了 ⇒ 删除前必须 `channel/view` 快照归档 + dry-run + 显式确认。
   - **`updated_channel` 事件的 body 里没有「操作人」字段**（body 就是 Channel 对象）⇒ 无法从事件判断「是谁改的」，**防回环只能靠幂等 + 本地时间窗**（见 `03`）。
   - **删除分组是否会级联删除子频道，官方没有说明**（T4，高危，只能在隔离测试服验证）。

## 还需要用户确认的三件事（不阻塞本次调研）

1. **业务目标**：这套「频道维护」是要做哪种？(a) 按职业/玩法**自动创建并同步**一套频道；(b) 定期**清理空语音频道**、重排顺序；(c) 频道权限按角色**批量对齐**；(d) 只做**漂移检测与告警**（只读）。四者的写操作风险与设计差异很大。
2. **目标服务器 `guild_id` 与运行环境**：有没有**可自由折腾的测试服务器**（结论 10 与 `02` 里多条高危探针只能在隔离环境做）。
3. **要不要我接着写探针脚本**：`02` 里的清单可以直接变成一份 Node 脚本（默认只读、写操作需显式开关）。若要写，需要约定 token 存放位置（例如 `kook/token.txt`，且必须进 `.gitignore`）。
