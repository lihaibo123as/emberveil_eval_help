# KOOK 频道维护 · 对接方案草案

> 取证时间：2026-10-09｜前置事实见 `01-频道维护接口调研.md`，验证项见 `02-待实测清单.md`
> 本文件是**设计草案**（未实现）：把 `01` 里的接口事实收敛成一套「能安全跑在真实服务器上」的维护方案。
> 设计里凡是依赖未实测语义的地方，都用 **【待 Tn】** 显式标出，实现时先看 `02` 的结论，不要凭猜写死。

---

## 1. 先定业务目标（决定整个设计）

| 目标 | 写操作量 | 风险 | 设计重点 |
| --- | --- | --- | --- |
| (a) 按分类**自动创建并同步**一套频道 | 高 | 中 | 幂等 reconcile + 所有权账本 + 删除闸门 |
| (b) 定期**清理空语音频道 / 重排顺序** | 中 | 高（影响真实用户） | 「空」的判定口径 + 保护名单 + 只删自己建的 |
| (c) 按角色**批量对齐频道权限** | 高 | 高（可能锁死自己） | 权限矩阵声明 + 差集写入 + 自保检查 |
| (d) 只做**漂移检测与告警**（只读） | 零 | 零 | 快照比对 + 告警输出（**建议的第一阶段**） |

> 建议落地顺序就是 **(d) → (a/b/c)**：先只读巡检跑通「读全量 + 算差异 + 出报告」，把模型跑对，再开写权限。

## 2. 架构：声明式期望状态 + 对账循环

```
       ┌────────────────────┐        ┌──────────────────────┐
       │ desired.json       │        │ ledger.json          │
       │ （人写的期望状态）  │        │ （系统自写的账本）    │
       └─────────┬──────────┘        └──────────┬───────────┘
                 │                              │
                 ▼                              ▼
        ┌──────────────────────────────────────────────┐
        │            reconcile（一次对账）              │
        │  1 读现状（guild/view 或 channel/list+view）  │
        │  2 计算 diff（只对「我们管的」对象）          │
        │  3 生成 plan（纯数据，可打印/可审）           │
        │  4 apply（串行 + 限流自适应 + 写后回读）       │
        │  5 更新 ledger + 落 reconcile 日志            │
        └──────────────────────────────────────────────┘
                 ▲                              │
                 │ 触发                          │ 事件（仅触发/告警，不直接改）
        ┌────────┴───────────┐        ┌─────────▼─────────────┐
        │ 定时（如 10min/次） │        │ WS 事件流              │
        │ 手动（命令）        │        │ added/updated/deleted_ │
        └────────────────────┘        │ channel、updated_role… │
                                       └───────────────────────┘
```

**为什么是「对账」而不是「事件驱动直接改」**：
`updated_channel` 事件**没有操作人字段**（`01` §8.2），无法区分「我们自己刚改的」与「别人改的」；而事件还有延迟与重投可能（T13）。所以**唯一可靠的写入口 = 对账循环**，事件只用来「提前触发一次对账」和「发现人工改动」。

## 3. 数据模型

### 3.1 `desired.json`（人写的期望状态）

关键设计：**顺序用数组下标表达，不写 `level` 字面值** —— 因为 `level` 的方向/同值语义未定义（【待 T2】），把「顺序」抽象成数组，映射公式实现时再定。

```jsonc
{
  "guild_id": "0000000000000000",
  "prefix": "",                       // 可选：频道名前缀，如 "[EV] "（对玩家可见，需团队同意）
  "categories": [
    {
      "key": "cat_raid",              // 稳定 key（账本主键），与频道名的关系由 name 字段决定
      "name": "团队副本",
      "order": 1,
      "channels": [
        { "key": "ch_raid_signup", "name": "报名", "type": 1,
          "topic": "团本报名与排班", "slow_mode": 0,
          "order": 1, "managed": true },
        { "key": "ch_raid_voice", "name": "团队语音", "type": 2,
          "limit_amount": 25, "voice_quality": "3", "order": 2, "managed": true }
      ]
    }
  ],
  "permission_profiles": {            // 复用的权限模板，按 key 引用
    "members_read": { "allow": 2048, "deny": 0 },
    "guest_none":   { "allow": 0,    "deny": 2048 }
  },
  "overwrites": [                     // 频道级覆写：与 (频道key, 目标) 绑定
    { "channel": "ch_raid_signup", "type": "role_id", "value": "0",
      "profile": "members_read" },
    { "channel": "ch_raid_signup", "type": "role_id", "value": "123456",
      "profile": "guest_none" }
  ],
  "deletions": { "enabled": false },  // 默认禁止删除；显式打开后才允许 reconcile 删对象
  "notify": { "channel": "ch_notice", "onChange": true }  // 可选：变更通知（吃消息配额！见 §8）
}
```

### 3.2 `ledger.json`（系统自写的账本，**唯一的所有权依据**）

```jsonc
{
  "guild_id": "0000000000000000",
  "updatedAt": 1760000000000,
  "categories": {
    "cat_raid": { "id": "1234…", "name": "团队副本", "createdAt": 1759… }
  },
  "channels": {
    "ch_raid_signup": {
      "id": "5678…", "name": "报名", "type": 1, "parentKey": "cat_raid",
      "lastAppliedAt": 1760000000000,      // 我们最后一次写它的时间（防回环用）
      "lastAppliedHash": "sha1:…",         // 我们写下去的期望值指纹（判断漂移用）
      "overwrites": [ { "type":"role_id", "value":"0", "allow":2048, "deny":0 } ]
    }
  },
  "archive": [                              // 删除前的快照（channel/view 原样存档）
    { "at": 1760000000000, "reason": "removed from desired", "channel": { /* channel/view 全量 */ } }
  ]
}
```

**所有权判定（三级，优先级从高到低）**：

1. **账本里有这个 key ⇒ 是我们的**（最可靠，`channel_id` 为主键；T5 若证明 id 会复用，则加 `createdAt` 双键校验）。
2. **`parent_id` ∈ 账本里的受管分组 ⇒ 视为受管**（用于「有人往我们的分组里塞了个频道」这种情况；此时先**告警**，不自动删）。
3. **都不匹配 ⇒ 不碰**。绝不靠「名字像」来判断所有权（名字会被人改，也可能撞名）。

> **为什么不能用 `topic` 当所有权标记**：`topic` **只在文字频道有效**（`01` §3.4），分组与语音频道根本存不了标记。名字前缀可行但**对玩家可见**，所以只能作辅助，不能作唯一依据。→ 账本 + 分组边界是唯一稳的组合。

## 4. reconcile 算法（伪代码）

```js
async function reconcile(desired, ledger, mode /* "report" | "plan" | "apply" */) {
  // ── 0. 只读现状：一次拿全景（T14 确认 guild/view 是否全量；若否，退化为 list(type=0/1/2) × N 页）
  const guild = await api.get("/guild/view", { guild_id: desired.guild_id });
  const roles = indexBy(guild.roles, "role_id");
  const byId  = indexBy(guild.channels, "id");
  const byParent = groupBy(guild.channels, "parent_id");

  // ── 1. 差异计算（只算受管对象：账本命中 或 parent 属于受管分组）
  const diff = { createCat: [], createCh: [], update: [], overwrite: [], delete: [] };
  for (const cat of desired.categories) {
    const cur = ledger.categories[cat.key] && byId[ledger.categories[cat.key].id];
    if (!cur) { diff.createCat.push(cat); continue; }              // 新建分组
    if (cur.name !== cat.name) diff.update.push({ id: cur.id, patch: { name: cat.name } });
    if (levelOf(cat, desired) !== cur.level)                        // 【待 T2】顺序→level 映射
      diff.update.push({ id: cur.id, patch: { level: levelOf(cat, desired) } });

    for (const ch of cat.channels) {
      const c = ledger.channels[ch.key] && byId[ledger.channels[ch.key].id];
      if (!c) { diff.createCh.push({ ...ch, parentId: cur.id }); continue; }
      const patch = {};
      if (c.name !== ch.name) patch.name = ch.name;
      if (!eq(c.topic, ch.topic ?? "")) patch.topic = ch.topic ?? "";   // 仅文字频道
      if (!eq(c.slow_mode, toSlowMode(ch.slow_mode))) patch.slow_mode = toSlowMode(ch.slow_mode); // 【待 T3】
      if (ch.type === 2 && !eq(c.limit_amount, ch.limit_amount)) patch.limit_amount = ch.limit_amount;
      if (ch.type === 2 && !eq(c.voice_quality, ch.voice_quality)) patch.voice_quality = ch.voice_quality;
      if (levelOf(ch, desired) !== c.level) patch.level = levelOf(ch, desired);
      if (Object.keys(patch).length) diff.update.push({ id: c.id, patch });
      diff.overwrite.push(...diffOverwrites(ch.key, c.id, desired, ledger));  // 需要 channel-role/index 读现状
    }
  }

  // ── 2. 删除：只有显式开启 + 只有账本命中 + 只有「从 desired 里被移除」的 key
  if (desired.deletions.enabled) { /* 收集待删，见 §6 三道闸门 */ }

  // ── 3. 计划输出（plan 模式到此为止，人看这份计划）
  logPlan(diff);
  if (mode !== "apply") return diff;

  // ── 4. 应用：严格串行 + 限流自适应 + 写后回读
  await limiter.run(async () => {
    for (const cat of diff.createCat) { const r = await api.post("/channel/create", {guild_id, name: cat.name, is_category: 1}); ledger.add(cat.key, r); }
    for (const ch of diff.createCh)  { /* create → update(补 topic/slow/level) → 更新 ledger */ }
    for (const u of diff.update)     { await api.post("/channel/update", { channel_id: u.id, ...u.patch }); markApplied(u.id); }
    for (const o of diff.overwrite)  { await api.post("/channel-role/" + (o.exists ? "update" : "create"), o); }
    for (const d of diff.delete)     { await archive(d.id); await api.post("/channel/delete", { channel_id: d.id }); ledger.remove(d.id); }
  });

  // ── 5. 收尾：写回账本（含 lastAppliedAt / lastAppliedHash）+ 落日志 + 可选通知
  await ledger.save();
  return diff;
}
```

**四条不可省的纪律**：

1. **先读后写、无差异不写**（`patch` 为空就不发请求）—— 直接决定了请求量（`01` §10.1）与事件风暴的大小。
2. **写后回读自证**：`update` 之后对该频道 `channel/view` 回读，比对期望值（防止「接口返回 0 但没生效」，也顺便抓 T3 那种单位坑）。
3. **严格串行**：不并发写（限流桶 + 事件风暴 + 顺序依赖，三者都不允许并发）。
4. **每步落账**：写到一半崩了，下次跑能接着对（账本是崩溃恢复的唯一依据）。

## 5. 防回环（自触发事件）

事实：我们自己 `update` 一个频道，服务端也会推 `updated_channel` 给我们，而事件 body **没有操作人**（`01` §8.2）。

三层防护：

| 层 | 机制 | 说明 |
| --- | --- | --- |
| L1 | **幂等 reconcile** | 收到事件后触发一次对账，但此时「现状 == 期望」⇒ 无差异 ⇒ **不产生任何写请求** ⇒ 循环自然终止。**这是最根本的一层**，不要依赖其他层兜底 |
| L2 | **冻结窗** | 账本记 `lastAppliedAt`；事件到达时若 `now - lastAppliedAt < FROZEN_MS`（初值取 T13 实测延迟上界 × 2，暂定 30s）且该频道的现状与 `lastAppliedHash` 一致 ⇒ **丢弃该事件**（只记一行日志） |
| L3 | **触发器去抖 + 合并** | 事件触发对账前先合并：`debounce(5s)`，且**同一时刻只允许一个 reconcile 在跑**（锁），避免事件风暴把对账排队堆起来 |

**判定标准**：写 1 次频道名 ⇒ 期望「1 个 `updated_channel` 事件进来 → 触发 1 次对账 → **0 次写请求**」。这条判据必须在真机验证（T13 顺带）。

## 6. 安全闸门（三级 + 删除专属）

### 三级运行模式

| 模式 | 行为 | 默认 |
| --- | --- | --- |
| `report` | 只读 + 差异报告（人类可读 + JSONL 落盘） | ✅ 默认 |
| `plan` | report + 打印**将要执行的请求清单**（method/url/body 一行一条，可直接审） | 手动 |
| `apply` | 真正写 | 必须显式 `--apply` |

### 删除专属三道闸门（缺一不可）

1. **配置层**：`desired.deletions.enabled` 必须为 `true`（默认 false）。
2. **命令层**：`--allow-delete` 显式开关；且**逐条打印待删对象**（key / id / name / 类型 / 原父分组），要求二次输入确认（如输入服务器名前 6 位）。
3. **数据层**：删除前先 `channel/view` **全量快照**存进 `ledger.archive`（含 `permission_overwrites`/`permission_users`）—— 因为**没有恢复接口**（`01` §11），这份快照是人工重建的唯一依据。

其他硬规则：

- **保护名单**：`default_channel_id` / `welcome_channel_id`（`guild/view` 里有）**永不删除、永不移动**。
- **不许动非受管对象**：任何写操作的 `channel_id` 必须先通过 §3.2 的所有权判定。
- **分组写覆写要额外警告**：分组上的 `channel-role/*` 会**级联到所有 `permission_sync=1` 的子频道**（`01` §4.1）⇒ 涉及分组的权限变更一律要求 `plan` 模式先看清单。
- **自保检查（权限类改动必做）**：写之前先算「改完之后机器人自己还能不能看到/管理这个频道」；算不出来（【未文档化】）就在 `plan` 输出里**红字提示人工确认**。绝不给自己角色的 bit11(查看) 写 deny。

## 7. 限流与请求节流

```js
class Limiter {
  // 事实（01 §10）：桶值未公开，只能读响应头自适应
  updateFromHeaders(h) {
    this.limit     = +h["x-rate-limit-limit"]     || this.limit;
    this.remaining = +h["x-rate-limit-remaining"] ?? this.remaining;
    this.resetSec  = +h["x-rate-limit-reset"]     || this.resetSec;
    this.bucket    = h["x-rate-limit-bucket"]     || this.bucket;   // 用于分别记账
    this.global    = h["x-rate-limit-global"];
  }
  async acquire() {
    if (this.remaining <= 1) await sleep((this.resetSec + 1) * 1000);   // 主动等，别等 429
    await sleep(this.minIntervalMs);                                    // 全局最小间隔（初值 350ms）
  }
  async on429(res) {
    const wait = (+res.headers["x-rate-limit-reset"] || 5) * 1000;
    await sleep(wait + jitter());
    this.consecutive429++;
    if (this.consecutive429 >= 3) { this.halt(); }    // 连撞 3 次：停机等人看，别硬闯（可能被禁用 bot）
    else { this.minIntervalMs *= 2; }                  // 指数加间隔
  }
}
```

- **`X-Rate-Limit-*` 必须逐响应记录**（不只记 429），这才是「提前知道快到顶」的唯一来源。
- 桶按 `X-Rate-Limit-Bucket` **分别记账**（读桶与写桶大概率不同，【待 T9】）。
- **收到官方警告（或连续 429）⇒ 立刻停机**：官方明确「多次超速可能撤销密钥/禁用 bot」，宁可少做也不能把机器人玩死。
- 读操作可以做**本地缓存**（频道全量快照缓存 10~30s），因为「不写就不需要最新」，能显著降低读请求量。

## 8. 消息配额预算（别把账号额度烧光）

事实（`01` §9）：**账号级 10,000 条/日**，`message/create` 与 `message/update` **都计数**，北京时间 12:00 重置。

| 场景 | 预算策略 |
| --- | --- |
| 每次 reconcile 都发一条变更通知 | ❌ 禁止。改成「**只有真的有变更**才发」，且**合并成一条**（一次对账最多 1 条） |
| 频道导航 / 规则说明 | 用**一条固定消息 + `message/update` 复用**（注意 update 也计数）⇒ 一天最多刷几次，别每分钟刷 |
| 大改动（如批量重排） | 先 `plan` 输出给人看，**人确认后**再决定要不要公告 |
| 兜底 | 本地记「今日已发条数」，超过自设阈值（如 200）就**停发通知只落日志** |

另：官方明确建议**过滤掉机器人自己发的消息再回应**，否则多机器人互相应答会刷爆配额并**被封禁**。

## 9. 事件消费者（WS）要点

| 要点 | 做法 |
| --- | --- |
| 连接 | `GET /gateway/index?compress=0`（**建议不压缩**，省掉 zlib 那一层不确定性；若用压缩，注意服务端下发是 binary deflate，上行不压缩） |
| 心跳 | 每 30s ±5s 发 PING，**带「已处理成功的最大 sn」**；6s 内没 PONG ⇒ 判超时 → 重连流程 |
| `sn` | **落盘持久化**（重启后可 resume）；乱序先入 buffer；重复 `sn` 直接丢 |
| RECONNECT | 收到后：清空本地 `sn` 与消息队列 → 重新取 gateway（官方原文要求） |
| 重连次序 | 2 次 PING(2s,4s) → 2 次 resume(8s,16s) → 重新取 gateway（指数退避，上限 60s，可无限重试） |
| 事件过滤 | **只保留关心的事件**（`added/updated/deleted_channel`、`added/updated/deleted_role`、`deleted_guild`）；其余直接丢（尤其是频道消息，避免与消息处理逻辑纠缠） |
| 事件处理动作 | **只做三件**：① 记录日志；② 触发一次对账（去抖+锁）；③ 若现状与账本不符且**不是我们改的** ⇒ 打「人工漂移」告警 |
| 明确不做 | **绝不**在事件处理里直接调写接口（那是回环与并发写的来源） |

`deleted_guild` 的处理：机器人在该服务器里的一切账本条目应标记为「失效」（不要立刻清空，便于事后查证）。

## 10. 落地阶段（每阶段都有独立验收）

| 阶段 | 内容 | 验收判据 |
| --- | --- | --- |
| **P0** | 只读巡检：读 `guild/view` → 与 `desired.json` 比对 → 出人类可读报告 + JSONL | 连跑 3 次，**请求数 = 3 次（1 次/次）**、**0 写请求**、报告内容稳定 |
| **P1** | `plan` 模式：输出将要发的请求清单（含 body 与原因） | 人为把 `desired.json` 改一处 → 清单恰好多出**那一条**；不改则清单为空 |
| **P2** | `apply` 但**只允许 create/update 命名与简介**（权限、删除都还关着） | 改 3 处 → 恰好 3 次写请求 + 3 次回读自证；再跑一次 ⇒ **0 次写请求**（幂等） |
| **P3** | 开启权限覆写（先只对**频道**，不对分组） | 权限矩阵改 1 条 → 恰 1 次 `channel-role/update`；`index` 回读与期望一致 |
| **P4** | 开启排序重排 | 顺序变更后请求数 = 需改的频道数（不是全部频道数） |
| **P5** | 接入 WS 事件触发 | 手工改一个频道 ⇒ 事件到达 → 触发对账 → **0 写请求**（防回环成立） |
| **P6** | 开启删除（含快照归档） | 从 desired 移除一个自建频道 ⇒ 快照进 `archive` + 1 次 delete；非受管频道**一个字节都不动** |
| **P7** | 语音维护（可选，风险最高） | 「空语音频道清理」只对**账本命中 + 无人在内**的频道生效；保护名单与在语音中的人一律不碰 |
