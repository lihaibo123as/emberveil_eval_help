# KOOK 频道维护 · 待实测清单

> 取证时间：2026-10-09｜配套文档：`01-频道维护接口调研.md`（事实）· `03-对接方案草案.md`（设计）
> 本清单里每一条都是**官方文档没写清 / 自相矛盾 / 行为高危**，**只有真机验证过才能当结论写进代码**。

## 0. 施工前提（先满足再动手）

| 前提 | 原因 |
| --- | --- |
| **一个可自由折腾的测试服务器** | T4（删分组）、T10（频道名边界）、T12（数量上限）都会**真实创建/删除频道**，绝不能在正式服做 |
| **一个测试机器人**（独立于将来上线的那个） | 避免把正式机器人的 token/配置搞脏；也能对照「权限不足」的表现 |
| 机器人角色给到**频道管理（bit5=32）** | T8 要对比「有/没有该权限」的行为差异 |
| token 只从环境变量/本地文件读，**绝不进日志、绝不提交** | 仓库是公开的（README 面向玩家），token 泄漏=服务器被人乱改 |
| 一次只验一个假设 | 多条同时改，出问题分不清是哪条的因果（本项目一贯纪律） |

**只读探针模板**（读任何接口都用这个形态，注意 `Authorization` 头与 `Accept-Language`）：

```bash
# 建议先取「机器人自己所在服务器列表」，拿到 guild_id
curl -sS -D- -H "Authorization: Bot $KOOK_TOKEN" \
  "https://www.kookapp.cn/api/v3/guild/list?page_size=50"

# 读频道列表（注意：不传 type 只会拿到文字频道！要看全量请分别传 0/1/2 或改用 guild/view）
curl -sS -D- -H "Authorization: Bot $KOOK_TOKEN" \
  "https://www.kookapp.cn/api/v3/channel/list?guild_id=$GUILD_ID&page_size=50"

# 读全量频道 + 角色（冷启动首选，1 次请求）
curl -sS -D- -H "Authorization: Bot $KOOK_TOKEN" \
  "https://www.kookapp.cn/api/v3/guild/view?guild_id=$GUILD_ID"
```

`-D-` 是为了**把响应头打出来** —— 限流头（`X-Rate-Limit-*`）只有响应头里才有（T9 必须用它）。

**写探针模板**：

```bash
curl -sS -D- -X POST -H "Authorization: Bot $KOOK_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"guild_id":"'"$GUILD_ID"'","name":"__probe_tmp","type":1}' \
  "https://www.kookapp.cn/api/v3/channel/create"
```

> ⚠️ 写探针一律**用可识别的临时名**（如 `__probe_*` 前缀）+ **用完立刻删**，并在测试服操作。

## T1（高优先）｜频道三事件到底推不推、推给谁

| 项 | 内容 |
| --- | --- |
| 为什么必须实测 | 官方没写订阅机制，也没写「机器人无查看权限的频道是否推送事件」；而这决定了事件驱动架构可不可靠 |
| 操作 | ① 用机器人建一个测试频道 → 观察 WS 是否收到 `added_channel`；② 改名 → 是否收到 `updated_channel`；③ 删除 → 是否收到 `deleted_channel`；④ 把该频道的**查看权限**对机器人角色设为 `deny`（bit11），再改名 → 看是否还有事件 |
| 观察点 | `d.extra.type`、`d.extra.body.id`、`sn` 递增；`author_id` 是否恒为 `1` |
| 判定 | 收到=事件可用；收不到=只能轮询兜底（每个 reconcile 周期全量比对）。④ 若仍收到 ⇒ 可以「用事件当权限漂移的审计源」；收不到 ⇒ 只能靠对账 |
| 风险 | 低（只用自建测试频道） |

## T2（高优先）｜`level` 排序语义

| 项 | 内容 |
| --- | --- |
| 为什么 | 官方只写「频道排序」，**方向、相同值行为、分组与频道是否同序、取值范围全部未定义** |
| 操作 | 建 3 个文字频道 A/B/C，依次把 `level` 设为 `1`、`5`、`3`（同分组内），逐个 `channel/view` 读回；再造两个**不同分组**下的频道设相同 `level` 看顺序；再试 `level: 0` 与 `level: -1` |
| 观察点 | ① 客户端频道列表里的**人工可见顺序**；② `channel/view` 读回的 `level` 是否与写入一致（有无归一/钳制） |
| 判定 | 得出「小=靠前 or 大=靠前」+「同值时的次序规则（按 id？按创建时间？）」+「分组是否也吃 level 影响分组顺序」 |
| 风险 | 低（改的是自建频道的顺序；注意事后恢复） |

## T3（高优先）｜`slow_mode` 单位到底是 ms 还是 s

| 项 | 内容 |
| --- | --- |
| 为什么 | `channel/update` 说 **ms** 并列了 ms 枚举；`channel/view` 与 `objects` 说 **秒**（§2.3 矛盾点） |
| 操作 | 对一个自建文字频道执行 `channel/update` 传 `slow_mode: 5000`，然后 `channel/view` 读回 `slow_mode`；再在**客户端界面上人工看**这条慢速设置显示多少 |
| 观察点 | 读回值 = `5000` ⇒ 后端按 ms 存储；读回值 = `5` ⇒ 按秒存储；客户端显示「5 秒」是最终裁判 |
| 判定 | 记录「写用什么单位、读用什么单位」，并把结论写回 `01` 的 §2.3（**这条不改完，读→写往返会差 1000 倍**） |
| 风险 | 低（只影响一个自建频道的发言频率限制，验完改回 `0`） |

## T4（最高危）｜删除分组会不会级联删除子频道

| 项 | 内容 |
| --- | --- |
| 为什么 | 官方**完全没写**。如果会级联，一个误删分组的操作 = 一次事故 |
| 操作 | **仅在隔离测试服**：建分组 `__probe_cat` → 在其中建 2 个频道（`__probe_a`/`__probe_b`）→ `channel/delete` 删掉**分组** → 立即 `channel/list`（`parent_id=分组id`）与逐个 `channel/view` 子频道 |
| 观察点 | 子频道是「一起消失」还是「`parent_id` 变空/变 0 被移出分组」 |
| 判定 | 得出级联结论 → 写进 `01` 与删分组的代码注释；**若是级联，则删除分组必须比删除频道更严格地要求确认** |
| 风险 | **极高**（可能一次删掉整组频道）⇒ 只允许在测试服、且子频道是探针自建的 |

## T5｜删除后的 id 会不会被复用 / `deleted_channel` 是否必到

| 项 | 内容 |
| --- | --- |
| 为什么 | 账本以 `channel_id` 为主键，若 id 会复用，历史账目会串味 |
| 操作 | 建 `__probe_x` → 记 id → 删除 → 再建一个新频道 → 比对 id 是否相同；同时记录删前删后 `deleted_channel` 事件 |
| 判定 | id 不复用 ⇒ 账本安全；若复用 ⇒ 账本必须带 `createdAt` 双键校验 |
| 风险 | 低 |

## T6｜`channel/create` 传 `is_category=1` 时其它字段的行为

| 项 | 内容 |
| --- | --- |
| 为什么 | 官方写「只接收 `guild_id`、`name`、`is_category` 三个字段」，**多传是报错还是静默忽略**没写 |
| 操作 | ① 传 `is_category:1` + `limit_amount:10` + `type:2` → 看返回与错误；② 建完后 `channel/view` 看 `is_category`/`type`/`limit_amount` 实际值 |
| 判定 | 「报错」⇒ 参数校验要严格；「静默忽略」⇒ 参数构造要显式剔除 |
| 风险 | 低（可能多出一个分组，事后删掉） |

## T7（高优先）｜权限覆写语义

| 项 | 内容 |
| --- | --- |
| 为什么 | `role_id: 0` 的含义、分组覆写对 `permission_sync` 子频道的实际作用、`allow`/`deny` 同位置冲突时的优先级，官方都没定义清楚 |
| 操作 | ① 对自建频道 `channel-role/create` 传 `type:"role_id", value:"0"` → 看返回的 `role_id` 与其在客户端「频道权限」界面上对应的对象（是否 `@全体成员`）；② 对分组写一条覆写（如 deny 发布消息），观察 `permission_sync=1` 的子频道是否同步、`=0` 的是否不变；③ 对同一对象同时给 `allow` 与 `deny` 同一位，看最终生效 |
| 观察点 | `channel-role/index` 读回值 + 客户端界面上的人工核对 |
| 判定 | 得到「role_id=0 是谁」+「sync 级联的确切范围」+「allow/deny 冲突规则」 |
| 风险 | 中（权限改错会让机器人自己失去频道可见性 ⇒ **先给机器人自己的角色留后路**，别把 bit11 对自己 deny；用完立刻清理覆写） |

## T8｜权限不足时的表现（错误分类基准）

| 项 | 内容 |
| --- | --- |
| 为什么 | 没有文档化错误码表（§1.1），错误分类只能靠实测采集 |
| 操作 | ① 用一个**没有**频道管理权限的机器人 token 调 `channel/create`；② 调 `channel/update` 一个不存在/已被删的 `channel_id`；③ 用错误 token 调任一接口（HTTP 层）；④ 故意传错参数类型（`limit_amount: "abc"`） |
| 观察点 | HTTP 状态码 + `{code, message}` 原文（分别用 `Accept-Language: zh-CN` 与 `en-US` 各来一次） |
| 判定 | 建立最小错误码字典（至少区分：权限不足 / 对象不存在 / 参数错误 / 鉴权失败 / 限流） |
| 风险 | 低 |

## T9（高优先）｜限流桶的真实值

| 项 | 内容 |
| --- | --- |
| 为什么 | 官方只给示例（`Limit: 5`、`Reset: 14`），桶名与容量未公开；而频道维护是「写多」的场景 |
| 操作 | 对**读**接口：连续 20 次 `channel/list`，每次记录完整 `X-Rate-Limit-*` 头；对**写**接口：在测试服连续建 10 个 `__probe_*` 频道（建完就删），记录头与 429 出现的时机与 `Reset` 值 |
| 观察点 | `X-Rate-Limit-Bucket` 的名字（是否为 `channel/create` 这类按接口分桶）、`Limit` 值、`Reset` 单位（秒）、429 时的头 |
| 判定 | 得出「每个接口桶容量 / 窗口 / 429 退避应按哪个头」⇒ 写成代码里的自适应参数（**不要写死**） |
| 风险 | 中（连续写会制造真实频道；且**多次超速可能被警告/禁用 bot** ⇒ 不要用正式机器人做，也不要在正式服做；一旦收到警告立即停止） |

## T10｜频道名/简介的边界

| 项 | 内容 |
| --- | --- |
| 为什么 | 官方没写名称长度、允许字符、是否允许重名、是否允许换行/emoji |
| 操作 | 在测试服依次建 `__probe_` + 下列名称：超长（64/128 字符）、纯空格、含换行、含 emoji、与已存在频道同名、含 `#`/`@` 等特殊字符；每次记录成功与否与 `message` |
| 判定 | 得出「可接受的名称格式与上限」⇒ 生成频道名时先本地校验，避免半个批次失败 |
| 风险 | 低（可能多出几个频道，随手删） |

## T11｜分组能否嵌套

| 项 | 内容 |
| --- | --- |
| 为什么 | 「一个分组下再建分组」官方没写；而维护脚本若按二级结构生成频道，会直接踩这一条 |
| 操作 | 建分组 `__probe_cat1` → 以 `parent_id=__probe_cat1` + `is_category:1` 建 `__probe_cat2` → 看返回与 `channel/view` 的 `parent_id` |
| 判定 | 允许 ⇒ 可做二级结构；不允许 ⇒ 设计里所有频道只能一层分组 |
| 风险 | 低 |

## T12｜单服频道数量上限

| 项 | 内容 |
| --- | --- |
| 为什么 | 容量上限决定了「按玩法铺频道」的方案能铺多大 |
| 操作 | 在测试服**批量创建文字频道**直到失败（用循环 + 每次读限流头 + 失败即停），记录失败点与 `message`；同时观察是否有别的限制（如分组数上限） |
| 判定 | 得到实际上限（同时确认失败是「配额」还是「限流」——看 `code` 与 HTTP 状态） |
| 风险 | 中（会造出大量频道；**必须在测试服**，且验证完要清理） |

## T13｜事件与 HTTP 返回的先后（防回环设计依赖）

| 项 | 内容 |
| --- | --- |
| 为什么 | 设计「自己写入后冻结事件窗」需要知道：自己触发的 `updated_channel` 大约在写入后多久到、会不会重复 |
| 操作 | 记录一次 `channel/update` 的**本地时间戳**与 HTTP 返回时间，同时记录收到的该频道 `updated_channel` 事件的 `msg_timestamp`；重复 5 次取范围 |
| 判定 | 得到「事件延迟上界」与「是否可能重复投递」⇒ 决定冻结窗时长与幂等判据 |
| 风险 | 低 |

## T14｜`guild/view` 的 `channels[]` 是否「全量且含分组」

| 项 | 内容 |
| --- | --- |
| 为什么 | `guild/view` 是冷启动首选；若它漏掉分组或语音频道，就得退回 `channel/list` 分 type 拉三遍 |
| 操作 | 对照 `guild/view.channels[]` 与 `channel/list`（`type` 分别传 0/1/2 三次）的结果做集合比对 |
| 判定 | 相等 ⇒ 冷启动只调 1 次；不等 ⇒ 记录差异（可能是权限过滤，也可能是字段精简） |
| 风险 | 低（只读） |

## T15｜Webhook 与 WebSocket 互斥的实际表现

| 项 | 内容 |
| --- | --- |
| 为什么 | 官方明确两者互斥，但「切换后另一端是静默不推还是报错」没写；选型前要确认 |
| 操作 | 在开发者后台配置回调地址（webhook）后，观察原来的 WS 连接是否还能收到事件（含是否被服务端断开、是否收到 RECONNECT） |

| 风险 | 低/中（会改变机器人配置；**别在正式机器人上做**，或做前记录原配置以便还原） |

## T16｜`intent`（事件订阅掩码）到底是什么、能不能改

| 项 | 内容 |
| --- | --- |
| 为什么 | `user/me` 的返回里有 `intent`（官方注「事件订阅掩码，默认为 `-1` 接收所有」，示例里出现过 `255`），但**没有任何一处文档说明各位的含义或设置方法**。这决定了能不能「只订阅频道/角色事件」从而少收噪音 |
| 操作 | ① `GET /api/v3/user/me` 读回 `intent` 实际值；② 在开发者后台找有没有「订阅事件/权限」配置项（截图留证）；③ 若后台可改，改成只留频道类再观察事件流变化（**在测试机器人上做**） |
| 判定 | 若 `intent` 可配 ⇒ 事件面可裁剪，事件消费者能省掉大量过滤；若不可配 ⇒ 只能客户端过滤（当前实现假设） |
| 风险 | 低（只读为主） |

## T17（高优先）｜帖子频道（type=4）发布链路

| 项 | 内容 |
| --- | --- |
| 为什么 | 用户服务器里的「插件发布」频道实测 `type=4` = **帖子频道**，而文档的中心是「普通频道消息」，两套接口完全不同；主楼能否带 `file` 模块、审核状态如何，全都没验证过 |
| 操作 | ① `GET /channel/view?target_id=5336773639081280` 确认 `type=4`；② `GET /category/list?channel_id=…` 看分区；③ 用 `thread/create` 发一条测试帖（`title` + `content` = 卡片 JSON，卡片里带 1 个 `file` 模块指向已 `asset/create` 上传的小文件）；④ 回读 `thread/view?thread_id=…` 看 `status` 与 `medias`；⑤ 在客户端里确认「文件是可下载附件」而不是「一行文字」；⑥ 试 `thread/reply` 回一条 |
| 观察点 | `status`（1 审核中/2 通过/3 编辑审核中）；`medias` 数组里是否出现该文件；客户端里附件的可点性 |
| 判定 | ① 若 `file` 模块在主楼**可用** ⇒ 发布直接用卡片（现脚本就是这么做的）；② 若**不可用** ⇒ 退回 `--mode link`（只在主楼写文字 + GitHub/Gitee 发布页链接，不附包）；③ 若 `status=1` 长期不通过 ⇒ 该频道开了审核，发布后需人工在客户端放行（脚本要如实提示） |
| 风险 | 中（会在公开频道发一条测试帖；验完用 `thread/delete` 删掉） |

## 建议的执行顺序

1. **只读三连**：T14（guild/view vs channel/list）、T9-读（限流头）、T8（错误码采集）⇒ 零风险，先把「事实底座」补齐。
2. **低危写测**：T2 → T3 → T6 → T10 → T11 → T13（都在自建测试频道上）。
3. **中危**：T7（权限覆写，注意别锁死自己）、T9-写（限流写桶）、T12（容量）。
4. **高危**：T4（删分组级联）—— 确认测试服、确认子频道是探针自建、确认已备份账本后再做。
5. 每验完一条，**回写** `01-频道维护接口调研.md` 对应小节（把【未文档化】改成【已实测 + 日期 + 现象】），并把这行从本清单删掉/勾掉。
